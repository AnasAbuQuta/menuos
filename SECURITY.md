# MenuOS Security Review

## Controls verified for v1.0

- Passwords use Laravel's hashed cast and registration/login Form Requests.
- Sanctum bearer tokens expire and logout deletes the current token.
- Protected endpoints use `auth:sanctum`; policies and ownership-scoped validation enforce one restaurant per owner and tenant isolation.
- Owner-controlled IDs are prohibited or resolved through restaurant-scoped queries.
- Uploads require decoded images, explicit JPEG/PNG/WebP MIME and extension allowlists, and a 2 MB limit. Stored filenames are generated by Laravel.
- Public menu and analytics endpoints are rate-limited. Analytics subject IDs are verified against the target restaurant.
- Analytics stores an HMAC-SHA256 visitor hash, not the browser identifier, IP, user agent, or other personal data.
- API Resources expose allowlisted fields. User passwords/tokens and restaurant owner IDs are not included in public resources.
- Responses set nosniff, frame denial, strict referrer policy, a restrictive permissions policy, and same-site resource policy.
- Production templates disable debug output, restrict CORS, enable secure/encrypted cookies, and prefix Sanctum tokens.
- No committed secrets, debug dumps, raw SQL interpolation, wildcard production CORS, or sensitive analytics logs were found.

## Operational requirements

- Use HTTPS everywhere and add HSTS at the reverse proxy after validation.
- Keep secrets in a platform secret manager; never store them in repository files, build logs, shell history, or support messages.
- Restrict database and object-storage credentials to the minimum required operations.
- Configure a frontend CSP at the web server/CDN. Start in report-only mode because API/storage origins differ by deployment.
- Patch PHP, Laravel, Node, and server packages regularly. Run `composer audit --locked` and `npm audit --audit-level=high` before every release.
- Restrict production logs and backups; both may contain restaurant contact details.
- Rotate compromised Sanctum tokens by deleting rows in `personal_access_tokens`; rotate `APP_KEY` only with a planned `APP_PREVIOUS_KEYS` transition.

## Accepted limitations

- The MVP stores bearer tokens in `localStorage`; XSS prevention and CSP are therefore critical. A future security sprint may evaluate same-site HttpOnly cookie authentication without changing it during launch stabilization.
- Dynamic restaurant social metadata is client-rendered. Social crawlers that do not execute JavaScript require a deployment-level prerender/edge metadata solution.
- Rate limits are IP-based and should use a shared cache store when running multiple API nodes.
- No email verification, MFA, security event dashboard, or automated account recovery exists in v1.0.

Report suspected vulnerabilities privately to the deployment owner. Do not open a public issue containing exploit details or secrets.
